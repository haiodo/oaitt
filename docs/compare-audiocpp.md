# Сравнение с audio.cpp

audio.cpp (`0xShug0/audio.cpp`) - движок инференса аудио-моделей на ggml: ASR, TTS,
клонирование голоса, VAD, диаризация, разделение источников, музыка, в одном нативном
рантайме и с OpenAI-совместимым сервером. Проверяли, есть ли от него польза для нас:
скорость GigaAM, качество на Golos, поведение под нагрузкой и цена перехода на его API.

Коротко: **для текущего проекта выгоды нет.** На GigaAM RNNT он медленнее нашего Swift,
качество то же, а OpenAI-API не покрывает наш контракт (нет auth, нет ogg, нет
verbose_json). CTC-вариант в 1.7 раза быстрее нашего, но нам он не нужен. Цифры ниже
оставлены, чтобы не перемерять, если появятся TTS, диаризация или CUDA-стенд.

## Стенд и методика

MacBook Pro (Mac16,5), Apple M4 Max, 48 GB, macOS 27.2. Аудио для скорости -
`sample-data/Sobolev_Andrey_1_0_00-2_17.ogg` (137.4s), для качества - Golos test,
первые 395 записей, протокол из [benchmarks.md](benchmarks.md).

- Сборка: `scripts/build_metal.sh --model-set custom --models gigaam_asr,supertonic
  --target audiocpp_cli` (и `audiocpp_server`). Release, Metal, ggml из сабмодуля.
- Скорость: `--metrics`, `metrics.wall_ms` - чистый инференс без загрузки весов; три
  прогона, медиана.
- Качество: гипотезы через `--batch-audio-dir` (395 wav за один процесс), WER тем же
  нормализатором, что `scripts/eval_golos_wer.py` (числа прописью, `ё -> е`, без пунктуации).
- **Проверка методики**: наши MLX-модели, прогнанные тем же скриптом на тех же wav, дали
  5.08% (CTC) и 4.38% (RNNT) - ровно опубликованные числа readme. Значит, стенд считает
  то же самое, и разница ниже - не артефакт счёта.

## Как устроено

Реестр загрузчиков по семействам: семейство берётся из метаданных GGUF, поэтому один
бинарник обслуживает 130+ семейств, а `--family` лишь ускоряет старт. На семейство
создаётся сессия под конкретную пару задача/режим (`asr`+`offline`).

ASR (GigaAM, `src/models/gigaam_asr/session.cpp`): ресемпл в 16 кГц -> нарезка по тихим
точкам до 25 с -> мел-фронтенд -> conformer -> жадный CTC/RNNT -> SentencePiece. На GPU
фронтенд следующего чанка считается в `std::async`, пока идёт энкодер текущего.
Таймстемпы слов - из кадров эмиссии токенов, не forced alignment.

TTS (Supertonic, `src/models/supertonic/`): текстовый чанкер (300 симв.) -> duration
predictor -> text encoder -> flow-matching денойзер (8 шагов) -> вокодер, 44.1 кГц.
Пресетный голос - векторы стиля из GGUF, клонирования нет.

## Скорость, 137.4s

| модель | медиана wall | xRT | пик footprint |
|---|---|---|---|
| v3-ctc / e2e-ctc f16 | 220 / 214 мс | **~620x** | 743 МБ |
| multilingual-ctc f16 | 221 мс | ~620x | 744 МБ |
| v3-rnnt f16 | 758 мс | **181x** | 734 МБ |
| v3-e2e-rnnt f16 | 663 мс | 204x | 738 МБ |
| oaitt Swift CTC (для сравнения) | 380 мс | 361x | ~4.7 ГБ |
| oaitt Swift RNNT | 610 мс | 225x | - |

- CTC: audio.cpp в **1.7 раза быстрее** нашего Swift, памяти в 6 раз меньше.
- RNNT (наш основной режим): **на 20% медленнее**, но в тех же пределах, что и разброс
  стенда. Паритета, как у CrispASR, не получилось.
- Батч 395 коротких записей в одном процессе: ctc 6.1 с, rnnt 14.6 с - с загрузкой весов.

TTS Supertonic-3: 9.4 с речи за 155 мс warm (61x realtime), первый прогон 707 мс.
`--mode streaming` - псевдострим по текстовым чанкам: `--text-chunk-size 40` даёт
отдельные `chunk_N.wav` по ~135 мс и склейку в финальный файл.

## Качество, Golos test, 395 записей

| модель | общий набор | без латиницы |
|---|---|---|
| audio.cpp v3-**ctc** | **2.67%** | 2.67% (n=395) |
| audio.cpp v3-**rnnt** | **2.21%** | 2.21% (n=395) |
| audio.cpp v3-e2e-ctc | 7.44% | 5.13% (n=366) |
| audio.cpp v3-e2e-rnnt | 6.62% | 4.42% (n=369) |
| audio.cpp multilingual-ctc (на русском) | 5.03% | 5.03% |
| oaitt CTC (MLX) | 7.39% | **5.08%** (n=366) |
| oaitt RNNT (MLX) | 6.62% | **4.38%** (n=368) |

Расхождение звучит драматично, но его нет:

- **e2e-варианты совпадают с нашими до 0.05 п.п.** - это один и тот же чекпоинт, качество
  идентичное. E2E в audio.cpp и есть тот режим, в котором работает наш MLX-порт.
- 2.21-2.67% у plain-вариантов - артефакт протокола, а не превосходство. Plain не делает
  ITN, числа выходят словами; E2E пишет `60 000`, и нормализатор превращает это в
  «шестьдесят ноль ноль ноль». Ровно та ловушка, о которой предупреждает
  [benchmarks.md](benchmarks.md).
- Единственное реальное отличие в тексте на длинном файле - **швы чанков**: у нас 20 с
  фиксированно, у них 25 с по тихим точкам, поэтому на 137-секундной записи тексты
  расходятся примерно на треть слов. На коротких записях Golos расхождения нет.

`multilingual-ctc` на английском тексте Supertonic: `"supertonic three is a small text
to speech model running locally on ggml and metal it is fast"` - слово в слово. `v3` на
английском, как и ожидается, рассыпается.

## Под нагрузкой (HTTP, `/v1/audio/transcriptions`)

Один процесс сервера, файл 137.4s, клиент - 8-16 запросов на уровень:

| | CTC | | | RNNT | | |
|---|---|---|---|---|---|---|
| concurrency | throughput | p50 | max | throughput | p50 | max |
| 1 | 660x | 208 мс | 209 мс | 197x | 696 мс | 702 мс |
| 2 | 676x | 405 мс | 415 мс | 199x | 1384 мс | 1387 мс |
| 4 | 675x | 809 мс | 822 мс | 198x | 2771 мс | 2789 мс |
| 8 | 676x | 1617 мс | 1632 мс | 195x | 4927 мс | 5635 мс |

- **Пропускная способность плоская, латентность растёт линейно**: внутри модели один
  мьютекс, запросы просто встают в очередь. Это повторяет вывод про Swift из
  [benchmarks.md](benchmarks.md): один процесс вширь не масштабируется, нужен пул процессов.
- `--parallel-jobs` с `"slots": 2` отвергается на старте:
  `model 'gigaam_asr' does not support the requested slots for this backend/task/mode
  (capacity=1)`. То есть параллельные слоты для GigaAM недоступны в принципе.
- Против наших чисел из [benchmarks.md](benchmarks.md) (RNNT через HTTP, c=4): Swift 144x,
  Python 181x, audio.cpp **198x**. Здесь он впереди - но за счёт более быстрого RNNT-декода
  на коротких чанках, а не за счёт concurrency.
- При c=8 максимум 5.6 с - очередь уже опасна для таймаутов клиента.

## ogg -> wav

Вход только WAV, поэтому в фасаде нужен транскод. Для файла 137.4s (уже 16 кГц mono,
ресемпл не нужен):

| способ | время |
|---|---|
| `ffmpeg -i in.ogg -ac 1 -ar 16000 -c:a pcm_s16le` | 145 мс |
| `soundfile.read` + `sf.write` (как в `src/utils/audio.py`) | 112 мс |

- Это ~0.1% длительности аудио и примерно половина CTC-инференса (206 мс). Для 10-секундного
  клипа - порядка 10 мс, линейно по длительности.
- **В фасаде это не регресс**: наш Python-сервис уже платит те же ~112 мс на декодирование
  ogg перед инференсом. Меняется только то, что транскод становится явным.
- Настоящий риск - не время, а объём: 241 КБ ogg против 4.19 МБ WAV, в 17.8 раза больше
  трафика на каждый запрос. По loopback это не видно, по сети будет видно.

## OpenAI-совместимость

`audiocpp_server` действительно отдаёт OpenAI-подобный API, обвес для базового сценария не
нужен. Проверено на живом сервере с GigaAM под id `whisper-1`:

| | OpenAI | audio.cpp |
|---|---|---|
| `/v1/audio/transcriptions` multipart | да | да, `file`/`model`/`language`/`prompt` |
| `/v1/audio/speech`, `/v1/models`, `/health` | да | да |
| `Authorization: Bearer` | обязателен | **нет аутентификации вообще**, заголовок игнорируется |
| входные форматы | mp3, mp4, ogg, flac, wav... | **только WAV**; `.ogg` -> `400 only WAV` |
| `response_format` | json/text/srt/vtt/verbose_json | игнорируется, всегда JSON с лишним `timing` |
| `verbose_json`, `words` | да | только `/transcriptions/details` (время в сэмплах) |
| `timestamp_granularities`, `temperature` | да | нет |
| голоса | alloy/nova/... | родные модели (`M1`-`F5`); `alloy` -> 500 |
| неизвестная модель | 404 `model_not_found` | 500 `server_error` (клиенты с ретраями на 5xx будут долбить) |

MP3/FLAC-вход возможен только со сборкой фронтенда из сабмодуля
`external/audio.cpp-server-frontends` (сейчас пустой) и `AUDIOCPP_SERVER_FRONTEND_MODULES=
audio_decode`. **OGG/Opus там нет даже так.**

## Вывод

Для текущего проекта audio.cpp не даёт выгоды:

- RNNT (основной режим) на 20% медленнее нашего Swift, качество то же;
- CTC быстрее в 1.7 раза, но нам он не нужен;
- OpenAI-API не покрывает наш контракт: нет auth, нет ogg, нет verbose_json и сегментов;
- 130+ чужих семейств моделей (TTS, диаризация, VAD, музыка) сейчас не нужны.

Пересмотреть стоит, если: понадобится локальный TTS/диаризация/VAD без Python; появится
CUDA-стенд (авторы оптимизируют именно CUDA, Metal у них "for portability"); или если
наш основной режим сместится на CTC.

Второй жизни у варианта "audio.cpp как движок, наш сервис как фасад" тоже нет: чтобы
заменить MLX, нужно выиграть в скорости, а выигрыша на RNNT нет.

## Как воспроизвести

```bash
git clone --depth 1 https://github.com/0xShug0/audio.cpp
cd audio.cpp && ./scripts/build_metal.sh --model-set custom --models gigaam_asr,supertonic \
  --target audiocpp_cli
# веса: huggingface.co/audio-cpp/audio.cpp-gguf -> GigaAM-ASR-GGUF, Supertonic-3-GGUF
build/macos-metal-release/bin/audiocpp_cli --task asr --family gigaam_asr \
  --model gigaam-v3-e2e-ctc-f16.gguf --backend metal --audio audio-16k.wav --metrics
```

Golos-прогон: `--batch-audio-dir dir --text-out out/h.txt` даёт `h_NNN.txt` на каждую запись;
WER считается тем же нормализатором, что в `scripts/eval_golos_wer.py`.
Сервер: `audiocpp_server --config server.json`, модели в конфиге называются произвольно
(`whisper-1`, `tts-1`), поэтому клиенты с зашитым именем модели работают без правок.
