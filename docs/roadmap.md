# План работ

Пересобран 2026-09-11 из состояния репозитория: доки, история коммитов и замеры.
Каждый пункт опирается на цифры из [benchmarks.md](benchmarks.md), а не на идею «в лоб».

## Профиль нагрузки

Основной сценарий - бэкенд транскрипции созвонов. Стримящий клиент режет дорожку каждого
участника по VAD на короткие чанки (медиана 2.5s) и шлёт их в сервис отдельными
HTTP-запросами; по завершении записи у клиента остаётся и полная дорожка целиком.
Все замеры, на которые опирается план, сняты на этом профиле: дорожки одного 92-минутного
рабочего созвона (4 говорящих, много англицизмов; треки вне репозитория) и синтетика
из Golos с точными границами реплик. Детали - [benchmarks.md](benchmarks.md).

## В работе: Parakeet TDT v3 в обеих реализациях

Решение (2026-09-12): Parakeet заходит в сервис - сначала движок в Python-версии,
потом собственный порт в Swift. Основа - замеры выше: 3.99% WER на общем наборе Golos
против 6.69% у GigaAM, word timestamps из коробки, 72x realtime. Готовых Swift-путей
избегаем сознательно: `mlx-audio-swift` не отдаёт timestamps и не чанкует длинное аудио,
FluidAudio - CoreML/ANE вместо MLX.

### Этап 1 - Python-движок `parakeet_mlx` (~0.5-1 дня)

Новый `src/asr/parakeet_mlx.py`, паттерн `gigaam_mlx.py`:

- `load_model()`: `from parakeet_mlx import from_pretrained`; дефолт
  `mlx-community/parakeet-tdt-0.6b-v3`, вариант `int8` -
  `sonic-speech/parakeet-tdt-0.6b-v3-int8` (+30% скорости, заявлен нулевой проигрыш
  в WER - проверить замером на Golos до включения в дефолты).
- `transcribe()`: временный wav (пакет принимает путь) -> `model.transcribe(path,
  chunk_duration, overlap_duration)`. Короткие чанки митингов - целиком, длинные файлы -
  120s/15s как в CLI пакета.
- Результат `AlignedResult` -> `TranscriptionResponse`: `sentences` -> сегменты;
  токены (start/duration/confidence) -> слова группировкой piece'ов по грани `▁`.
  Слово: start первого piece, end последнего, probability = min по piece'ам.
  Роуту `openai.py` правки не нужны - `seg.words` уже сериализуется в `verbose_json`.
  Это закрывает пункт 2 (word timestamps) для Python-версии.
- Lock-free режим как у GigaAM-MLX; idle unload наследуется от `ASRModel`.

Регистрация: `factory.py` (engine `parakeet_mlx`), `registry.py`
(`parakeet-tdt-v3`, `parakeet-tdt-v3-int8`), `config.py` (`PARAKEET_REPO_ID`,
`PARAKEET_CHUNK_SEC=120`, `PARAKEET_OVERLAP_SEC=15`), `requirements.txt`
(`parakeet-mlx`, только darwin/arm64 - без torch).

Тесты: движок в `test_engine_output.py`; мини-тест на непустой `words` в `verbose_json`
с валидными таймингами.

Верификация: `make check`; WER на Golos через `scripts/eval_golos_wer.py` (ожидание -
те же 3.99%, модель та же); слово-тайминги на `sample-data` глазами.

### Этап 2 - Swift-порт FastConformer-TDT (3-5 дней, отдельным заходом)

Запускается по итогам этапа 1 на реальных созвонах. Протокол `ASREngine.swift` уже
написан под вторую архитектуру - реестр, сервер и CLI не меняются.

1. `swift/Sources/GigaAM/Parakeet.swift`: FastConformer-энкодер (24 слоя, d_model 1024,
   8 голов, FFN 4096, rel_pos attention с bias-таблицами - не RoPE, depthwise-conv
   субсэмплинг x8), TDT-предиктор (embedding + 2-слойный LSTM 640), joint с duration
   head (5 длительностей, blank 8192). Весовые ключи - из safetensors
   `mlx-community/parakeet-tdt-0.6b-v3` через `@ModuleInfo(key:)`. Из `Model.swift`
   переиспользуются паттерн LSTM-декода и `rnntDecodeBatch` как основа TDT-батч-декода
   (TDT проще - duration позволяет пропускать кадры).
2. `Mel.swift`: параметризация `nMels` (64 -> 128) без ломания GigaAM; mel-параметры
   сверить с `parakeet_mlx` на Python.
3. `ParakeetTranscriber`: реализация `ASREngine`, сегменты из токенов, bucket-padding
   сохраняется.
4. Подключение: `Registry.known` + `parakeet-tdt-v3`, `ModelOptions` в CLI,
   `Supervisor`/`ModelDownloader` приложения (веса `data/parakeet_tdt_v3/`, докачка).
5. Верификация: побуквенное совпадение с Python-портом на тест-файлах (как делали для
   RNNT), bench в `benchmarks.md`, `make check`.

### Риски

- Mel-параметры Parakeet (128 bins) отличаются от GigaAM (64) - на этапе 1 пакет
  считает mel сам, на этапе 2 сверять с его реализацией.
- Rel_pos attention с bias - новая для кодовой базы конструкция, отлаживать сверкой
  промежуточных тензоров с Python-портом.
- int8-вариант - качество проверить до дефолтов.

## Ближайшие задачи

Порядок по соотношению «польза / стоимость». Для каждого пункта указано, что добавляется
в сам сервис.

### 1. Полный проход по накопленному аудио

Замеры показывают, что два прохода по одной и той же дорожке принципиально разные:

- полный проход по всей дорожке дешевле суммы VAD-чанков в 2.6 раза (367x против 141x
  realtime): чанки платят оверхед на вызов, а один длинный файл идёт большими батчами;
- стриминговая нарезка теряет качество: короткие реплики-подтверждения выпадают целиком
  (65 пустых ответов у самого говорливого участника), а фразы, разрезанные пополам,
  дают выдумку на обрубке («Список должен» -> «Ножем»). Расхождение двух путей - 7.84%
  по словам на живом созвоне.

Что добавляется в сервис:

- поддержка сценария «финализация»: клиент досылает полную дорожку после завершения
  записи, сервис возвращает транскрипт полного прохода; он уже работает - узкое место
  не в скорости, а в удобстве клиента. 6 часов аудио при этом проходят за 56s.
- правила объединения со стриминговым результатом на стороне клиента опираются на
  причину закрытия чанка. Стримящий клиент уже шлёт её в заголовке `X-End-Reason`,
  чанк, закрытый по `max_duration`, оборван на полуслове - соседей таких чанков
  склеивать нельзя. Сервис этот заголовок сейчас не читает; стоит принять его в метаданные
  результата, чтобы объединение можно было делать надёжно.

Готовность: на дорожке живого созвона короткие реплики появляются в итоговом транскрипте,
расхождение объединённого результата с полным проходом ниже стриминговых 7.84%.

### 2. Word-level timestamps

Клиенты запрашивают `timestamp_granularities[] = word`, но GigaAM покадровых меток
не отдаёт - параметр молча игнорируется (`src/asr/gigaam_mlx.py` логирует и пропускает).
Без word-таймингов также не построить честную метрику «ошибка по чанку» из
[benchmarks.md](benchmarks.md): сегменты 10-20s нельзя сопоставить с чанками по 2.4s.

- Два пути. Свой forced alignment по покадровым вероятностям CTC-головы (она уже есть
  в Python и Swift) - работает для GigaAM, но его надо писать. Готовый -
  **Parakeet TDT v3**: word timestamps из коробки, и на общем наборе Golos он уже
  качественнее GigaAM (3.99% против 6.69%, [benchmarks.md](benchmarks.md)).
  Принято: закрывается этапом 1 раздела «В работе» выше.
- Готовность: `verbose_json` отдаёт `words`; ошибка границы слова на синтетике с точными
  границами - p50 не хуже 100 мс.

### 3. Доменные термины и англицизмы

Замер на живом созвоне ([benchmarks.md](benchmarks.md), «Англицизмы») показал, что ни одна
модель задачу не решает: GigaAM роняет знакомые термины (`на Джаво и Task`), Whisper
транслитерирует доменные названия. Ошибки GigaAM и Whisper при этом независимы - их
расхождение в конкретном месте почти наверняка означает доменный термин.

- База: Qwen3-ASR-1.7B уже подключена и замерена (15% WER на Golos против 4-6% у
  конкурентов - как единственная модель для русского не годится,
  [benchmarks.md](benchmarks.md)). Проверить её механизм hotwords
  (`generate(hotwords=[...])`) именно на англицизмах: возможно, контекст закроет доменные
  термины даже при более низком базовом WER.
- Параллельно: у Parakeet v3 английское внутри русского текста транслитерируется
  кириллицей - уже сейчас поведение лучше, чем у всех; проверить его на тех же
  фрагментах с англицизмами.
- Если hotwords не взлетят: постобработка расхождений GigaAM vs Whisper глоссарием через LLM.

### 4. Multilingual в Swift

У multilingual-модели другая архитектура (charwise CTC, окна 20s с перекрытием 2s), в
Swift-порт она не портирована - приложение не обслуживает казахский, киргизский и
узбекский, хотя Python-версия умеет ([macos-app.md](macos-app.md), «Ограничения»).

- Альтернатива своему порту: Parakeet TDT v3 - 25 европейских языков (ru, uk, kk нет,
  но pl/bg/cs есть), качество и скорость замерены ([benchmarks.md](benchmarks.md)).
  Решить, что дешевле: порт GigaAM Multilingual на Swift или движок Parakeet рядом.

### 5. CPU-резерв (сделано 2026-09-23)

## Проверено и отвергнуто - не повторять

| Идея | Почему нет |
|---|---|
| Батчер чанков (общая очередь чанков разных запросов) | Убивает перекрытие CPU и GPU: RNNT 256x -> 93x, CTC 388x -> 209x на реальной нарезке ([benchmarks.md](benchmarks.md)) |
| Батчинг CTC внутри запроса | Откат 508x -> 340x: у CTC один argmax, поточная схема держит GPU занятым лучше |
| Пул моделей внутри одного Swift-процесса | 143x против 144x у одной копии - сериализация процессная, масштабирование только процессами |
| CTC vs RNNT расхождение как сигнал неуверенности | Головы сидят на одном энкодере и ошибаются согласованно; расхождение означает «CTC ошибся», не «вход трудный» |
| Склейка чанков ради качества | WER не меняется, проблема не в длине |
| Чанки длиннее 30s | Attention растёт как O(T^2): 60s медленнее двух по 30s |
