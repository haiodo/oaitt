# Замеры

Стенд: MacBook Pro (Mac16,5), Apple M4 Max, 16 ядер, 48 GB. Аудио -
`sample-data/Sobolev_Andrey_1_0_00-2_17.ogg`, 137.4s. `xRT` - во сколько раз быстрее
реального времени.

Замеры latency и throughput делались на частично загруженной машине; относительные
сравнения внутри одной таблицы достоверны, абсолютные числа могут плыть на 10-20%.

## Python против Swift

Чистый инференс, in-process, 16 итераций, без HTTP:

| concurrency | CTC Python | CTC Swift | RNNT Python | RNNT Swift |
|---|---|---|---|---|
| 1 | 271x | **496x** | 105x | **142x** |
| 2 | 447x | 506x | 201x | 150x |
| 4 | **602x** | 514x | 280x | 150x |
| 8 | 574x | 512x | **320x** | 143x |

Swift быстрее в один поток, но упирается в плато уже при concurrency 1. Python
масштабируется потоками и берёт более высокий пик.

Масштабирование Swift процессами:

| процессов | CTC | RNNT |
|---|---|---|
| 1 | 508x | 144x |
| 2 | **668x** | 263x |
| 4 | 679x | **369x** |

Пул из 2-4 копий модели внутри одного процесса не даёт ничего: 143x против 144x у одной
копии. Сериализация процессная, не на уровне весов.

## Стабильность и память

120 запросов подряд, concurrency 4, RNNT, через HTTP, оба сервиса без единой ошибки:

| | Swift | Python |
|---|---|---|
| throughput | 144x | **181x** |
| p50 | 3.82s | **2.08s** |
| p95 | **3.99s** | 6.34s |
| max | **4.05s** | 9.50s |
| GPU active | 849 MB | 849 MB |
| GPU peak | **1681 MB** | 3007 MB |
| GPU cache | **3.6 GB** | 10.1 GB |

У Swift разброс p50 -> max - 6%, у Python - 4.5x. Суммарный след unified memory:
Swift ~4.7 GB, Python ~10.3 GB.

RSS напрямую сравнивать нельзя: у Swift MLX-буферы резидентны (1119 MB), у Python
учитываются в GPU cache, а не в RSS (191 MB).

## Стоимость чанка зависит от его длины

Один чанк, `B=1`:

| длина | CTC encode | CTC итого | CTC xRT | RNNT decode | RNNT итого | RNNT xRT |
|---|---|---|---|---|---|---|
| 1s | 9.8 ms | 10.0 ms | 100x | 5.4 ms | 14.7 ms | 68x |
| 2s | 11.4 ms | 11.5 ms | 173x | 10.7 ms | 21.9 ms | 91x |
| 5s | 13.1 ms | 13.3 ms | 375x | 25.3 ms | 38.0 ms | 131x |
| 10s | 17.7 ms | 17.9 ms | 557x | 46.3 ms | 63.9 ms | 156x |
| 20s | 31.0 ms | 31.3 ms | 639x | 94.6 ms | 125.7 ms | 159x |
| 30s | 46.6 ms | 46.9 ms | 640x | 140.8 ms | 188.1 ms | 160x |

У энкодера фиксированные накладные ~8.5 ms на вызов, поэтому чанк 1s стоит почти столько
же, сколько 5s. Длинные чанки тоже хуже - attention растёт как O(T^2): 40s -> 605x,
60s -> 562x. Оптимум одиночного чанка - 20-30s.

## Батчинг

CTC, только encode:

| длина чанка | B=1 | B=2 | B=4 | B=8 | B=16 |
|---|---|---|---|---|---|
| 2s | 168x | 320x | 505x | 641x | **780x** |
| 5s | 381x | 576x | 681x | 782x | **821x** |
| 10s | 541x | 671x | 774x | 802x | **825x** |
| 20s | 634x | 697x | 738x | **761x** | 740x |

RNNT с батчевым greedy-декодом:

| длина чанка | B=1 | B=4 | B=8 | B=16 |
|---|---|---|---|---|
| 2s | 62x | 149x | 331x | **505x** |
| 5s | 92x | 249x | 391x | **498x** |
| 10s | 105x | 270x | 394x | **456x** |
| 20s | 86x | 282x | 360x | **487x** |

Потолок GPU - ~820x (CTC) и ~500x (RNNT), достижим только батчем. На 20-секундных чанках
`B=1` уже даёт 634x, и там батчинг почти не нужен: это тот замер, на котором легко сделать
неверный вывод "батчинг не окупается". На коротких чанках выигрыш 4.6x (CTC) и 8.1x (RNNT).

## Батчер чанков: проверено, не окупается

Идея была очевидной: собирать чанки из разных запросов в общую очередь, группировать по
длине и гнать в модель одним тензором. Изолированный замер её поддерживал - 2s чанк в
одиночку даёт 168x, батч из 16 таких же 780x.

На живом коде вышло наоборот. Реальная нарезка VAD (21 чанк, медиана 2.5s), Python-движок:

| | c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|---|
| CTC без батчера | 205x | 345x | 381x | **388x** |
| CTC с батчером | 52x | 85x | 130x | 209x |
| RNNT без батчера | 84x | 154x | 231x | **256x** |
| RNNT с батчером | 36x | 48x | 66x | 93x |

Батчер с несколькими рабочими потоками тоже не спасает: RNNT при 2 потоках - 121x, при
4 - 115x, всё против 256x без него.

Причина в том, что узкое место не GPU, а сериализация вокруг него. Python выигрывает
именно за счёт многопоточности: пока один поток занят CPU-частью (mel, greedy-цикл),
другой держит GPU. Батчер сводит всё в один поток и это перекрытие убивает - выигрыш от
большего тензора не покрывает потерю параллелизма.

Что работает вместо него - батчевый greedy-декод RNNT внутри одного запроса: чанки
одного файла декодируются вместе, один GPU->CPU sync на кадр вместо одного на кадр на
чанк. На 137s файле дало 102x -> 196x, текст побайтово тот же. CTC не трогали: у него
один argmax, и поточный encode+decode держит GPU занятым лучше.

## Качество

Golos (`bond005/sberdevices_golos_10h_crowd`), первые 395 записей test-сплита, 1602s,
1949 слов:

| нормализация | CTC | RNNT |
|---|---|---|
| сырое сравнение | 12.67% | 11.85% |
| числа прописью | 7.23% | 6.46% |
| + без записей с латиницей | **5.08%** | **4.38%** |

Половина "ошибок" в лоб - не ошибки: GigaAM v3 e2e нормализует текст, эталон Golos записан
прописью (`четыреста двадцать` против `420`, `ютьюб риддл стрим` против `YouTube Riddle
Stream`). После приведения обеих сторон к прописи уровень совпадает с заявленным в карточке
модели.

Синтетический митинг: 150 записей Golos, склеенных с паузами 0.7-2.0s, room tone -80 dBFS,
818s, 749 слов, границы известны точно:

| сегментация | CTC | RNNT |
|---|---|---|
| идеальная (по эталонным границам) | 9.21% | **7.88%** |
| VAD love-agent как в проде | 18.96% | **16.96%** |
| VAD + фикс pre-buffer | 16.96% | 15.75% |
| VAD + фикс pre-buffer + пониженные пороги | 15.09% | **13.89%** |

Нарезка удваивает WER. Дефекты найдены в нарезке на стороне love-agent и там же
исправлены: pre-buffer отбрасывался почти целиком (на реальных митингах фикс даёт
-0.55 п.п. WER, дефолт 500 мс по замеру), порог VAD не опускался до тихих микрофонов.
Остаточный разрыв после фиксов - 6 п.п. против идеальной сегментации.

## Реальные митинги: два прохода и выбор модели

Замеры выше сняты на Golos и синтетике. Этот раздел - на живом материале: дорожки
участников одного 92-минутного рабочего митинга (48 кГц моно, речь про
разработку, англицизмов много). Эталонной расшифровки нет, поэтому здесь везде
**расхождение двух путей**, а не WER: оно показывает, что пути разошлись, но не кто прав.

### Стриминг против полного прохода

Стриминг - чанки от VAD love-agent, как в проде. Полный проход - вся дорожка целиком,
`splitAudio` режет её по минимуму энергии.

| участник | аудио | VAD покрыл | расхождение | полный проход | стриминг |
|---|---|---|---|---|---|
| участник A | 5546s | 66% (711 чанков) | 7.49% | 15.1s (367x) | 38.8s |
| участник B | 5126s | 14% (235) | 9.61% | 14.8s (346x) | 10.0s |
| участник C | 5209s | 9% (126) | 8.12% | 13.5s (385x) | 5.2s |
| участник D | 5182s | 3% (58) | 4.92% | 12.5s (414x) | 2.3s |

Взвешенно по словам - **7.84%** на 11084 словах.

**Второй проход дешевле первого.** У участника A полный проход 15.1s против 38.8s у
стриминга: один длинный файл идёт большими батчами, 711 мелких чанков платят оверхед на
каждом. Шесть часов аудио прошли за 56s суммарно - финализация после митинга не стоит
ничего.

Объём стриминг не теряет (7949 слов против 7785), но теряет два класса вещей: короткие
реплики-подтверждения выпадают целиком («Так», «Да», «Спасибо» - у участника A 65 пустых
ответов), а разрезанные пополам фразы дают выдумку на обрубке (`Список должен` ->
`Ножем`).

На синтетике разрыв был вдвое больше (16.96% против 7.88%). На живом митинге втрое
меньше: pre-buffer уже починен, а реальная речь громче склеек из Golos.

### CTC и RNNT: сигнала неуверенности не дают

Проверялась гипотеза «расхождение двух голов = вход трудный».

| | участник B | участник A | участник C |
|---|---|---|---|
| CTC vs RNNT, полный проход | 12.27% | 10.25% | 12.09% |
| CTC vs RNNT, стриминг | 10.23% | 10.30% | 9.81% |

Гипотеза **не подтвердилась**: обе головы сидят на одном энкодере и ошибаются
согласованно. Расхождение означает не «вход трудный», а «CTC ошибся» - на англицизмах он
разваливается заметно сильнее: `Джаво` -> `жavo`, названия внутренних сервисов
превращает в бессмыслицу.

Попытка посчитать корреляцию сигнала с ошибкой по чанкам дала мусор: сегменты полного
прохода длиной 10-20s сопоставлялись с чанками по 2.4s, отчего «ошибка» вышла 45-82% при
общем расхождении 9.6%. Для такой метрики нужны word-level тайминги с обеих сторон.

### Англицизмы: не чинит никто

Три фрагмента, где GigaAM RNNT ломается:

| время | GigaAM RNNT | GigaAM Multilingual | WhisperKit turbo |
|---|---|---|---|
| 4658s | `device Regista` | `девайс реджести` | `девайс регисти` |
| 1247s | `на Джаво и Task` | `на джаву и таск` | `на Java и Task` |

Ни одна модель не решает задачу. Whisper пишет латиницей знакомые ему термины (`Java`,
`Task`, `endpoint`, `GSM`) и транслитерирует доменные; GigaAM наоборот - берёт
`Registry`, но роняет `Java`. Multilingual транслитерирует всё.

Скорость на одном 5-минутном куске: GigaAM RNNT **92x**, WhisperKit large-v3-turbo
**5.8x** (CoreML, `brew install whisperkit-cli`), GigaAM Multilingual **149x** на полной
дорожке против 346x у RNNT.

Multilingual вдобавок вдвое хуже держит нарезку: своё stream vs full - 15.67% против
7.49% у RNNT. Вероятно из-за charwise CTC без внутренней языковой модели, но у неё своя
схема чанкинга (окна 20s с перекрытием 2s), так что сравнение не вполне чистое.

**Что из этого следует.** Ошибки GigaAM и Whisper независимы - в отличие от CTC и RNNT с
общим энкодером. Значит их расхождение в конкретном месте почти наверняка означает
доменный термин, и это рабочий детектор того, что стоит отдать LLM с глоссарием. А
единственный кандидат, решающий задачу до распознавания, а не после, - Qwen3-ASR с
`hotwords` (`mlx-audio`, параметр `generate(hotwords=[...])`). Не проверен.

## Сторонние модели на том же наборе

Сентябрь 2026, тот же Golos-протокол (395 записей test-сплита, 391 с эталоном, числа
прописью) и тот же файл 137.4s для скорости. Скрипт - `scripts/eval_golos_wer.py`.

Качество, два способа счёта. «Общий набор» - все 391 запись, сравнение моделей честное.
«Без латиницы» - записи, где и эталон, и гипотеза без латинских букв (старый протокол,
число сопоставимо с 4.38% из раздела «Качество»):

| модель | общий набор | без латиницы | примечание |
|---|---|---|---|
| GigaAM v3 RNNT (MLX, текущий) | 6.69% | 4.43% (n=364) | английские слова пишет латиницей - теряет эти записи |
| **Parakeet-TDT-0.6B-v3** (MLX) | **3.99%** | **3.79%** (n=389) | английское транслитерирует кириллицей, как эталон |
| Qwen3-ASR-1.7B 6bit (MLX) | 15.04% | 13.14% (n=371) | 8bit не помогает - 15.20% |
| Whisper large-v3-turbo | - | - | через faster-whisper, на качество не прогонялся |

Скорость на 137.4s, один запрос:

| модель | движок | xRT |
|---|---|---|
| GigaAM v3 RNNT | MLX Swift (текущий) | **142x** (241x батчем) |
| Parakeet TDT v3 | parakeet-mlx, GPU | ~140x |
| Qwen3-ASR-1.7B 6bit | mlx-audio, GPU | 36x |
| GigaAM v3 RNNT int8 | onnx-asr, CPU этой машины без docker | 110x |
| GigaAM v3 RNNT int8 | onnx-asr, CPU, docker arm64 | 67-75x |
| Whisper large-v3-turbo int8 | faster-whisper, CPU, docker | 19x |

Выводы:

- **Parakeet v3 - лучший мультиязычный кандидат**: качество на русском выше GigaAM
  (3.99% против 6.69% на общем наборе), вдвое быстрее Qwen3, word timestamps из коробки,
  25 европейских языков. Вес ~1.2 GB fp16.
- **Qwen3-ASR на русском разочаровала**: 15% против 4-6% у конкурентов, ошибки - мелкие
  подстановки («мурадяна» -> «мурадиана») по всему тексту. Квантование ни при чём.
  Остаётся интересной только ради hotwords - сценарий «англицизмов» она может закрыть
  не качеством, а контекстом; не проверено.
- **CPU-резерв жизнеспособен**: GigaAM int8 через onnx-asr даёт 67-75x realtime в docker
  (это в 3.5 раза быстрее faster-whisper на том же CPU) и текст того же качества, что
  GPU-версия. Но CTC-варианты GigaAM в onnx-asr 0.12 сломаны (мусор на выходе) - брать
  только RNNT. Упакован в движок `onnx_asr` и `Dockerfile.onnx`, см. раздел ниже.
- GigaAM на MLX остаётся самым быстрым движком для русского; CPU-вариант той же модели
  отстаёт в 1.3-2 раза и занимает все ядра, но служит резервом, если GPU-путь недоступен.

### Parakeet v3 в сервисе (движок `parakeet_mlx`)

Подключён как движок (`./run_parakeet_mlx.sh`), WER на том же наборе через код сервиса:

| вариант | WER (общий набор) | скорость, файл 137.4s | память весов |
|---|---|---|---|
| fp16 (дефолт) | **3.99%** | 140x | ~1.2 GB |
| int8 (sonic-speech, энкодер 8 бит gs64) | 4.05% | 153x | ~0.75 GB |
| Swift-порт, fp16 | 3.99%, текст совпадает на 391/391 | **185x** | ~1.2 GB GPU |

Замеры 2026-09-23, лучший из трёх прогонов при фоновой нагрузке (load average 6 - стенд
не бывает пустым); GigaAM Swift RNNT в тех же условиях - 288x. Swift-порт быстрее
Python-пакета в 1.3 раза, не в 1.7. int8 быстрее fp16 примерно на 9% и на длинном файле,
и на коротких чанках (391 запись Golos: fp16 29.7s, int8 26.7s), а не «в 1.7 раза на
длинных и медленнее на коротких», как было записано раньше. Стабильность Swift:
20 запросов подряд, память плоская - GPU active 1.24 GB, кеш ограничен 512 MB.

Swift-декод TDT переписан: проекция энкодера считается один раз на чанк, выход
LSTM-декодера переиспользуется на blank-шагах, синхронизация с GPU одна на шаг вместо
четырёх. Текст не изменился (Golos 391/391, оба часовых файла побайтно), скорость
выросла со 144x до 185x. До правки декод занимал 63% времени, энкодер 36%.

Bucket-padding (дополнение чанка нулями до целой секунды, как у GigaAM) Parakeet портит:
per-feature нормализация мела и attention без маски видят паддинг, WER 3.99% -> 4.41%,
а обрезка декода по реальной длине делает хуже (4.98%) - теряется хвостовая пунктуация.
Swift-порт Parakeet не паддит; без паддинга он ещё и быстрее (144x против 132x).

Длинные записи. Окна `parakeet-mlx` по 120s с перекрытием 15s теряли речь: на часовом
митинге пропало ~140s подряд - отдельный кусок 110s модель возвращает пустым. Python-движок
режет по паузам на куски до 20s, как Swift и GigaAM: потерянный кусок на месте, скорость
на часовых файлах 131-164x против 67-88x у окон. Parakeet чувствителен к границам чанков:
на митингах Python и Swift (разные нарезчики пауз, разный декод ogg) расходятся на 14-19%
слов, тогда как GigaAM Python и Swift - на 2-4%. Какая нарезка точнее, без эталона
не сказать. `verbose_json` отдаёт `words` с границами и вероятностью слов.

Два практических ограничения. Во-первых, mlx 0.32.x: eval графа Parakeet из не-главного
потока падает с «There is no Stream(cpu, N)» - все вызовы идут через один выделенный
поток инференса в движке (загрузка весов тоже в нём; загрузка в главном потоке не спасает).
Во-вторых, TDT-декод изредка даёт `<unk>`-всплеск на одной записи из 391 (metal-кернелы
не бит-детерминированы) - вероятность мала, но фильтр неуверенности по confidence
пер-токенных вероятностей должен её ловить.

### CPU через onnx-asr (движок `onnx_asr`, образ `Dockerfile.onnx`)

Замеры 2026-09-23, M4 Max под фоновой нагрузкой (load average 7-20), файл 137.4s,
Golos - те же 391 записи и тот же протокол нормализации, что выше.

| модель onnx-asr | WER (общий набор) | xRT нативно | xRT в docker | пунктуация |
|---|---|---|---|---|
| gigaam-v3-e2e-rnnt int8 (дефолт образа) | 6.79% | 84x | 47x | есть |
| gigaam-v3-rnnt int8 | **2.18%** | 93x | 55x | нет |
| gigaam-v3-rnnt fp32 | 2.23% | - | - | нет |
| nemo-parakeet-tdt-0.6b-v3 fp32 | 3.42% | - | 15-24x | есть, 25 языков |
| nemo-parakeet-tdt-0.6b-v3 int8 | - | - | 37x | **сломан**: срывается на английский |

Разница 6.79% против 2.18% - не качество распознавания, а протокол: e2e-модель пишет
английские слова латиницей, эталон Golos - кириллицей, каждое такое слово считается
ошибкой. Дефолтом в образе стоит e2e, чтобы текст совпадал с тем, что сервис отдаёт
на GPU-движках.

Целый файл в модель подавать нельзя - результат обрезается до одного предложения
(модели обучены на коротких отрезках), движок режет аудио по паузам на куски до 20s.
VAD из onnx-asr не используем: на коротких сегментах Parakeet сбивается на другой язык.

### MLX на CPU в Linux - тупик

MLX-CPU в контейнере даёт 6.6x realtime на Parakeet и 5.9x на GigaAM против 37-55x
у onnx-asr на том же железе. Плюс ловушка: колесо `mlx[cpu]` линкуется на эталонный
netlib BLAS из своего же wheel, а не на системный OpenBLAS, который ставит
`Dockerfile.mlx-cpu`. Из-за этого matmul 250x1024x4096 идёт 816ms вместо 12ms, и
GigaAM на MLX-CPU выдаёт 0.2x realtime. Лечится подменой библиотеки:

```dockerfile
RUN d=/usr/local/lib/python3.11/site-packages/mlx_cpu.libs; \
    ob=$(ls /usr/lib/*-linux-gnu/openblas-pthread/libopenblas.so.0); \
    for f in $d/libblas-*.so* $d/liblapack-*.so*; do ln -sf $ob $f; done
```

Даже после починки MLX-CPU в 9 раз медленнее onnx-asr, поэтому Swift-порт под Linux
(тот же CPU-бэкенд MLX) смысла не имеет.
